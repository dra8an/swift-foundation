### Test-placement bug (TZ mystery)

5. `swift test --filter "Hebrew"` showed 2 failures:
   `utcDate_allPolicyCombinations_matchGregorian` and
   `date_from_hebrewVsGregorian_atDSTBoundaries` — both reporting
   "America/Los_Angeles timezone unavailable".
6. **Root cause**: `TimeZone(identifier: "America/Los_Angeles")` requires
   `_TimeZoneICU` (linked via dynamic replacement from
   `FoundationInternationalization`). These tests were in
   `FoundationEssentialsTests`, which only links `FoundationEssentials` — so
   the dynamic replacement never applied and IANA identifiers returned nil.
   Same code existed on the 6.3 base; the tests were added in the `b47a560`
   commit and never actually ran successfully.
7. **Fix**: moved both tests to new file
   `Tests/FoundationInternationalizationTests/HebrewDSTPolicyParityTests.swift`.
   Removed from `HebrewCalendarTests.swift` with a comment pointing to the
   new location.

### Two new bugs found and fixed

9. **Bug #8 — multi-field `date(byAdding:)` at Kislev 30**: year and month were
   batched in a single decompose→adjust→clamp→reconstruct cycle. When adding
   1 year landed in a deficient year (Kislev 29 days), the day should clamp to
   29 before the month-add runs. **Fix** in `Calendar_Hebrew.swift`: split into
   two sequential operations matching
   `_CalendarGregorian.date(byAddingAndCarryingOverComponents)` pattern.

10. **Bug #9 — nanosecond extraction FP rounding**: Hebrew computed fractional
    seconds via chained subtractions (hours → minutes → seconds → fractional)
    then `Int((...).rounded())`. Gregorian does a single subtraction from the
    original value then `Int(...)` (truncation). **Fix** in
    `Calendar_Hebrew.swift`: replaced with
    `Int((localSeconds - localSeconds.rounded(.down)) * 1_000_000_000)`.

### Performance investigation

11. **Wrote `HebrewVsICUBenchmark.swift`** — side-by-side ICU vs Hebrew
    benchmarks with both GMT and America/Los_Angeles timezones, 10 runs each.

12. **Wrote `AllocationsBreakdown.swift`** — separated construction cost from
    arithmetic cost. Found the 35–44× allocation speedup comes from
    construction (57–71×: C++ `icu::HebrewCalendar` heap object vs Swift stored
    properties) plus day-add arithmetic (5–9×).

13. **Wrote `EnumerateBreakdown.swift`** — 3-layer breakdown of
    `nextThousandHanukkahs`. Found that `Calendar_Enumerate.swift`'s generic
    month-loop framework adds ~280 µs overhead per match, burying the 4.7×
    calendar-arithmetic advantage into a 1.3× headline number.

14. **Implemented `_CalendarHebrew.nextDate(after:matching:)`** — O(1)
    fast-path for `{month, day}` patterns. Computes target date directly via
    `hebrewFromFixed`/`fixedFromHebrew` instead of iterating months. Verified
    correct (20/20 dates match `enumerateDates`). Result: **513 ns/match vs
    ICU's 380 µs = 741×**. Lives entirely on `_CalendarHebrew` — no shared
    code modified.

    **Status: proof-of-concept only.** Nothing in production calls this method.
    `Calendar.enumerateDates` dispatches through `Calendar_Enumerate.swift`'s
    generic framework, which calls `_CalendarProtocol` methods one at a time.
    It has no way to reach `nextDate(after:matching:)` because `_calendar` is
    private to `Calendar.swift` and `_CalendarProtocol` doesn't include this
    method. To activate the fast-path in production, someone would need to
    touch shared Foundation code — either add the method to `_CalendarProtocol`
    (with a default nil return) or add a dispatch check in `Calendar.swift`.
    That's a conversation with the Foundation team, not something we can ship
    in the Hebrew port PR. The method is ready to wire up whenever the
    Foundation team is open to it.
