### Investigation: in-progress (NOT committed)

User goal: get the package benchmarks (ICU at ~1,000 μs, ours at 1,155 μs)
to similar 700×+ wins as local benchmarks show for fast-path patterns.

#### Why ours is slower on package benchmarks

The package benchmarks use patterns NOT in our fast path:
- `nextThousandThanksgivings`: `{m: 11, wd: 5, wdOrd: 4}` (4th Thursday).
- `RecurrenceRule*`: bypass `Calendar.enumerateDates` entirely. They use
  `Calendar._dates(startingAfter:matching:in:matchingPolicy:repeatedTimePolicy:)`
  which is internal and goes directly to `_unadjustedDates` /
  `_adjustedDate` in `Calendar_Enumerate.swift`. **Our fast-path wiring
  doesn't intercept this.**

So the slowness has two sources:
1. **Patterns we could fast-path but don't yet:**
   `{month, weekday, weekdayOrdinal}` (Thanksgiving / Labor Day style).
2. **Patterns we can't fast-path without touching shared code:**
   RecurrenceRule's internal enumerate. Would need to wire fast path
   into `_dates(...)` or `_unadjustedDates` to help.

#### What I almost did (interrupted before commit)

Was about to add a `{m, wd, wdOrd, h?, m?, s?}` fast path to
`_CalendarHebrew.nextDate(...)`. Algorithm:
- Find first day of target month in target year (one `fixedFromHebrew` call).
- Compute its weekday from RD mod 7.
- Find first occurrence of target weekday: `(targetWeekday - firstWd + 7) % 7` days from day 1.
- Add `(weekdayOrdinal - 1) * 7` days for the Nth occurrence.
- Negative `weekdayOrdinal` (-1 = "last", -2 = "second-to-last"): count back from `daysInMonth`.
- Validate result is in 1..daysInMonth.

This would make `nextThousandThanksgivings` and
`nextThousandThursdaysInTheFourthWeekOfNovember` go from ~1,000 µs to ~2 µs
(same shape as the existing `{m, d}` fast path).

The full implementation was prepared but not applied — see "Resume
checklist" below for the exact diff to apply on resume.

This won't help RecurrenceRule benchmarks (those bypass our wiring), but
it'll be a clean win for the enumerate-style ones. RecurrenceRule
optimization is a separate project (would need shared-code conversation
with Foundation team about wiring `_dates` to the protocol method).

### What helped vs what didn't

The clean attribution breaks down per-benchmark by which mechanism fired:

- **Single-combination short-circuit (v12 option 2)** — fires when every
  populated `_DateComponentCombinations` field has exactly one value.
  Skips the entire expansion-chain in `_unadjustedDates`. **All the
  big win on `RecurrenceRuleThanksgivings` and `RecurrenceRuleLaborDay`
  came from this.**
- **Helper hijacks (v11–v12 option 3)** — `dateAfterMatchingMonth`,
  `dateAfterMatchingWeekday`, `dateAfterMatchingWeekOfMonth`,
  `dateAfterMatchingWeekdayOrdinal`. **Smaller-than-hoped wins**:
  - `RecurrenceRuleThanksgivingMeals` saw -7% from `dateAfterMatchingMonth`
    fire (single-combination short-circuit doesn't fire because hours
    has 2 values).
  - `RecurrenceRuleBikeParties` saw 0% benefit — has no `months` field
    (so `dateAfterMatchingMonth` never invoked) and the `dateAfterMatchingWeekday`
    invocation is a no-op (the prior `dateAfterMatchingWeekOfMonth` hijack
    landed the date on the right weekday already).
  - `RecurrenceRuleDailyWithTimes` saw 0% benefit — `dateAfterMatchingMonth`
    never invoked (no `months`), and the existing helper walks are bounded
    short enough that hijacking saves only a few ns/call against ~3 µs
    of total per-match cost dominated by `_adjustedDate` + filter passes
    + 12-combination flatMap allocation.
- **Multi-combination patterns** retained their 0.50–0.92× ICU ratio
  because their per-match cost lives in machinery surrounding the
  helpers (12-way flatMap chain, `_adjustedDate` DST adjustment,
  `_limitX` filter passes), not in the helpers themselves.

### Safety analysis: the `_unadjustedDates` short-circuit

This is the largest behavioral change in the v8–v12 chain. The single-
combination short-circuit replaces ~7-step expansion chain with one
`_calendarNextDate` call. The user asked specifically how safe this is.

**What we have verified is safe**:
- The DATE matches between paths — `assert(count == 1000)` in the
  `RecurrenceRuleThanksgivings` benchmark passes, and our
  `nextMonthWeekdayOrdinalMatch` is verified vs ICU on 13 correctness
  probes in `EnumerateMicroProfile.extendedFastPath_correctnessVsICU`.
- Other calendars unaffected — Gregorian/etc. protocol default returns
  nil → falls through to existing path. `GregorianCalendar RecurrenceRule`
  tests pass unchanged.
- Defensive allowlist in `_singleCombinationDateComponents` rejects
  negative ordinals, multi-valued fields, `.every`-only weekdays,
  non-default policies. Anything outside the allowlist falls through.
- DST policy alignment — RecurrenceRule defaults to `repeatedTimePolicy:
  .first`; our `utcDate` uses `.former`. These are equivalent.
- 49/49 Hebrew + 165/165 Calendar tests pass.

**What we have NOT verified — the gaps**:
- **No ICU↔Hebrew RecurrenceRule parity probe.** Our existing parity
  probes (Suite A `HebrewICUComparisonProbe` and Suite B
  `HebrewPublicAPIComparisonProbe`) cover the primitives and direct
  `enumerateDates`/`dates(byMatching:)` paths but **don't exercise
  `RecurrenceRule` with Hebrew**. So we have no side-by-side comparison
  saying "ICU-Hebrew RecurrenceRule output exactly equals our-Hebrew
  RecurrenceRule output."
- **The result tuple's `DateComponents` differs.** Existing path
  produces tuples like `{weekOfMonth, weekday, hour, minute, second}`
  (no `month` — it gets shadowed during weekdays expansion at line
  871–893 of `Calendar_Recurrence.swift`). Our fast-path returns
  `{month, weekday, weekdayOrdinal, hour, minute, second}`. Both contain
  enough info to identify the date, but `_adjustedDate` does consume
  these components for validation and DST correction. **If
  `_adjustedDate` behaves differently with more vs fewer fields
  populated, our output could diverge from the existing path on edge
  cases I haven't tested.**
- **Edge cases not tested**:
  - Anchor that itself matches the pattern (off-by-one risk: existing
    path may include start; our `nextDate(after:)` strictly excludes it).
  - DST transition days where the match falls on a repeated/skipped hour.
  - End-of-search-range boundary cases.
  - Calendars with non-trivial month structure beyond Adar I leap-only
    (which is covered by our probes).

**Risk assessment**: medium. The benchmarks pass and our fast-path
matches ICU on standalone enumerate. But "matches ICU on
`enumerateDates`" doesn't automatically prove "matches existing-path
result through `_adjustedDate` on `RecurrenceRule`." A bug here would
manifest as silently-wrong date enumeration in user code — exactly the
kind of bug that takes months to surface.

**Mitigation pending**: write `HebrewRecurrenceRuleParityProbe` —
~50 RecurrenceRule shapes × ~10 dates each = ~500 comparisons against
`_CalendarICU(.hebrew)`. If those match, we have real confidence. Until
then, v12 stays in `backup/v12-*/` snapshot form, not committed.
