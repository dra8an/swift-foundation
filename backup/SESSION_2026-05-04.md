### Work completed this session

#### 1. Researched why DailyWithTimes was slow

Walked the full call chain in `Calendar_Recurrence.swift` and
`Calendar_Hebrew.swift`. Initial hypothesis (relax v13's
`_expandedDateComponents` to accept `.every(weekday)`) was wrong — for
daily-frequency rules, `weekdayAction == .limit` (RFC5545 BYDAY for
FREQ=DAILY is a limit), so weekdays aren't even in the combinations
passed to `_unadjustedDates`. The actual combinations are
`{hours: [9,10], minutes: [0,30], seconds: [<anchor.second>]}` — 4 cartesian
combinations, all time-only.

v13's `_expandedDateComponents` already produces the 4 valid time-only
DCs. The blocker was Hebrew's `nextDate` rejecting time-only
`DateComponents` at `Calendar_Hebrew.swift:1082`
(`!hasMonth && !hasDay && !hasWeekday → nil`). All 4 short-circuit
probes returned nil → fall through to slow path.

#### 2. v15 — Time-only fast path in Hebrew `nextDate`

~25 LOC change in `Calendar_Hebrew.swift` only (no shared-code edits):

- Removed the unconditional `!hasMonth && !hasDay && !hasWeekday → nil`
  rejection.
- Added a time-only branch gated on `{hour, minute, second}` all set
  (deliberately matches what `_unadjustedDates`'s short-circuits
  produce; partial time fields like `{hour: 9}` alone still fall
  through, preserving ICU semantics where unspecified means "any value").
- Added `nextTimeOfDayMatch(rd, currentSecsInDay, targetSecsInDay,
  forward, tz)` helper:
  - Forward: `targetRd = (target > current) ? rd : rd + 1`
  - Backward: `targetRd = (target < current) ? rd : rd - 1`
  - Returns `utcDate(fromRataDie: targetRd, secondsInDay: targetSecsInDay,
    repeatedTimePolicy: .former, skippedTimePolicy: .former)` — same
    pattern as `nextWeekdayMatch`. `_adjustedDate` (per-result in
    `_dates`) handles DST after.

With this in place, v13's existing cartesian short-circuit fires for
the 4 time-only DCs the daily-frequency path produces. `_limitWeekdays`
runs after `_dates` returns, dropping the 4 results on non-Mon/Tue/Wed
days — no expansion-chain change needed.

#### 6. Diagnosed `CurrentDateComponentsFromThanksgivings`

Bench at `BenchmarkCalendar.swift:128` uses **`currentCalendar`** (line
39: `Calendar.current` — captured at function entry, unchanged by the
parameterized identifier). The other 8 benchmarks use `cal` which is
the parameterized one. So this benchmark always measures
`.gregorian` via ICU; our Hebrew code never runs. That's why its
number is identical at ~5.7 µs/iter across c2668eb-pre → v15 with
"—" in the vs-ICU column.

Cost dominated by the per-iteration 16-field `dateComponents([era,
year, month, day, hour, minute, second, nanosecond, weekday,
weekdayOrdinal, quarter, weekOfMonth, weekOfYear, yearForWeekOfYear,
calendar, timeZone], from: result!)` call, not the enumerate.

Two follow-up options (deferred to v16 candidate):
- (A) one-line fix: change `currentCalendar` → `cal` in the bench body
  so it actually exercises Hebrew. Trivial, cosmetic — would show
  Hebrew at ~3.5× ICU on this shape (per existing `c2668eb`
  Hebrew-specific benches).
- (B) profile + optimize `_CalendarHebrew.dateComponents(_:from:)` for
  the 16-field shape (year already cached via YearData; weekday /
  weekOfMonth / weekOfYear / yearForWeekOfYear share substructure that
  could potentially be batched). Real perf work.

### Lessons learned

1. **Don't trust your first hypothesis.** I started v15 with the wrong
   plan ("relax `_expandedDateComponents` to accept `.every(weekday)`")
   and only realized it was wrong by tracing the actual call chain
   from `nextGroup()` → `_unadjustedDates`. Reading the code before
   writing the fix saved me from a useless edit.

2. **Save institutional knowledge in two places.** The bench command
   was in `SESSION_2026-05-01_to_03.md:200` but I didn't grep for it.
   Now it's in cross-session memory AND `BENCHMARKS_PACKAGE.md` so
   it's discoverable both ways.

3. **Watch out for empty-filter silence.** `swift package benchmark
   --filter <regex>` returns no results both when the regex matched
   nothing AND when something is wrong. Indistinguishable without
   reading the output carefully.
