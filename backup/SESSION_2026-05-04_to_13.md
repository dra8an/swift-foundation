#### 1. v15 — Time-only fast path closes the last laggard (2026-05-04)

Research walk-through of `Calendar_Recurrence.swift` revealed that for
daily-frequency rules, `weekdayAction == .limit` so weekdays aren't in
the combinations passed to `_unadjustedDates` — only `{hours, minutes,
seconds}`. v13's `_expandedDateComponents` already produced 4 valid
time-only DCs; the blocker was Hebrew's `nextDate` rejecting them at
the gate (`!hasMonth && !hasDay && !hasWeekday → nil`).

Fix: ~25 LOC in `Calendar_Hebrew.swift` only. Removed the time-only
rejection (gated on `{hour, minute, second}` all set), added
`nextTimeOfDayMatch` helper (same-day vs next-RD based on
`targetSecsInDay > currentSecsInDay`). v13's cartesian short-circuit
then fires for the 4 time-only DCs.

**Headline result**: `RecurrenceRuleDailyWithTimes` 3,024 → **191 µs**
(15.8× speedup, **~8× ICU**). Mallocs 3,742 → 151 (-96%). Other 8
benchmarks within ±5% noise. 178/178 + 62/62 tests, Suite C 0
divergences, 73,414/73,414 Hebcal days.

**8 of 9 calendar benchmarks now ≥8× ICU.**

Snapshot: `backup/v15-time-only-fast-path/`. Updates to BACKUPS.md,
BENCHMARKS_PACKAGE.md, HANDOFF.md, RECURRENCE_VS_NEXTDATE.md.

### Lessons from this period

1. **Keep both branches with minimum drift.** v16 + v17 syncs proved
   the workflow: changes happen on the right toolchain (Swift 6.4 for
   `port/hebrew-main`, Swift 6.3 for `port/hebrew`), back-sync as
   v-numbered snapshots so divergence is bounded. Don't try to do
   toolchain-sensitive work on the wrong machine.

2. **Document reviewer asks at the time they're filed.** PR comments
   #6 + #7 directly motivated `SHAREABLE_APIS.md`. Quoting the
   reviewer's exact words in the planning doc preserves intent
   across the gap between "review feedback" and "doing the refactor."

3. **Comprehensive pre-change snapshots (v16-frozen) pay off.** v17
   replaced 4 files. If anything had gone wrong, restoration was a
   plain `cp` from the snapshot. The cost (5 minutes to set up,
   ~50 KB of disk) is negligible vs the value (rollback insurance).

4. **Three required CI checks green on first push is a strong
   portability signal.** Especially Windows — couldn't verify
   locally on Intel iMac without that toolchain. Worth capturing in
   docs as a baseline so any later regression is obvious.
